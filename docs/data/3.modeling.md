# Mô hình dữ liệu (Data Modeling) — IPTV Viewing History

> **Công cụ (Tool):** dbt-core 1.7 + dbt-redshift
> **Kho dữ liệu (Warehouse):** AWS Redshift Serverless
> **Nguồn (Source):** Silver layer (S3 Parquet -> Redshift COPY)
> **Mô hình (Models):** 3‑layer: staging → intermediate → mart (Star Schema)
> **Chủ sở hữu (Owner):** Phuc Vinh
> **Cập nhật (Updated):** 12/04/2026

---

## 1. Tổng quan thiết kế

Đường ống dbt được tổ chức thành **3 tầng (3-layer modeling)** nhằm tách biệt rõ ràng trách nhiệm:

```
Silver (Redshift table: staging.viewing_history)
    |
    └── stg_iptv__logs_all      [view]   – Base model, chuẩn hóa kiểu dữ liệu
        ├── stg_iptv__logs          [view]   – Chỉ lấy dữ liệu hợp lệ (is_fraudulent = false)
        └── stg_iptv__logs_fraud    [view]   – Tách riêng dữ liệu lỗi/gian lận (is_fraudulent = true)
    |
    ├── int_enriched_sessions   [view]   – Làm giàu dữ liệu: join với seeds (phân khúc app, OUI lookup)
    |
    ├── dim_app                 [table]  – Dimension table: Ứng dụng/kênh
    ├── dim_device              [table]  – Dimension table: Thiết bị
    ├── dim_contract            [table]  – Dimension table: Hợp đồng
    ├── dim_date                [table]  – Dimension table: Ngày
    └── fact_views              [incremental] – Fact table: Sự kiện xem
```

**Lợi ích của kiến trúc 3 lớp:**
- **Tầng staging** giữ logic làm sạch nguyên thủy, không thay đổi khi logic nghiệp vụ phát triển.
- **Tầng intermediate** tập trung làm giàu và chuẩn bị dữ liệu cho nhiều mart khác nhau, tránh lặp code.
- **Tầng mart** triển khai Star Schema — các bảng dimension và fact dễ dàng tiêu thụ bởi BI và ad‑hoc queries.

## 2. Nguồn (Source) — `staging.viewing_history`

Đây là bảng Redshift được nạp bằng lệnh `COPY` từ S3 Silver (Parquet).

```yaml
# schema.yml (source definition)
sources:
  - name: staging
    schema: staging
    tables:
      - name: viewing_history
```

**Mapping tên cột từ Silver:**

| Tên gốc (Landing/Bronze) | Tên tại Silver / Redshift source |
|---|---|
| `_id` | `event_id` |
| `Contract` | `contract_id` |
| `Mac` | `device_mac` |
| `TotalDuration` | `total_duration_seconds` |
| `AppName` | `app_name` |
| `date` | `batch_date` |
| `fraud_reasons` | `fraud_reasons` |
| `is_fraudulent` | `is_fraudulent` |

Đổi tên được thực hiện trong Glue job. dbt nhận vào các cột đã được làm sạch cơ bản.

## 3. Tầng Staging

Gồm ba model dạng **view**:

### 3.1. `stg_iptv__logs_all` — Base Model

```sql
select
    event_id,
    contract_id,
    device_mac,
    app_name,
    total_duration_seconds,
    batch_date,
    round(total_duration_seconds / 60.0, 2)  as total_duration_minutes,
    left(batch_date, 4)                      as view_year,
    substring(batch_date, 5, 2)              as view_month,
    right(batch_date, 2)                     as view_day,
    is_fraudulent,
    fraud_reasons
from {{ source('staging', 'viewing_history') }}
```

**Thiết kế:**
- Ép kiểu (cast) và trích xuất ngày tháng (`view_year`, `view_month`, `view_day`).
- Mang theo toàn bộ dữ liệu hợp lệ và gian lận từ Silver.
- Materialized là **view** làm lõi phân dải cho cấp độ kế tiếp.

### 3.2. `stg_iptv__logs` — Dữ liệu hợp lệ

```sql
select 
    event_id,
    contract_id,
    device_mac,
    app_name,
    total_duration_seconds,
    total_duration_minutes,
    batch_date,
    view_year,
    view_month,
    view_day
from {{ ref('stg_iptv__logs_all') }}
where is_fraudulent = false
```

**Thiết kế:**
- Chỉ lấy dữ liệu hợp lệ (`is_fraudulent = false`) đưa vào hệ tính toán báo cáo (downstream).
- Việc lọc được gán tại model này giúp tránh việc nhồi dữ liệu lỗi vào các luồng metrics quan trọng.

### 3.3. `stg_iptv__logs_fraud` — Dữ liệu lỗi / gian lận

```sql
select *
from {{ ref('stg_iptv__logs_all') }}
where is_fraudulent = true
```

**Mục đích:**
- Tách riêng để dễ dàng giám sát, debug Audit & Security, mà không làm nhiễu luồng chính.

## 4. Tầng Intermediate — `int_enriched_sessions`

Model **view** này làm giàu dữ liệu `stg_iptv__logs` bằng cách join với các dữ liệu tham chiếu (seeds):

```sql
select
    l.event_id,
    l.contract_id,
    l.device_mac,
    l.app_name,
    l.total_duration_seconds,
    l.total_duration_minutes,
    l.batch_date,
    l.view_year,
    l.view_month,
    l.view_day,
    coalesce(s.app_segment, 'Unknown') as app_segment,
    coalesce(o.vendor, 'Unknown') as device_vendor
from {{ ref('stg_iptv__logs') }} l
left join {{ ref('app_segments') }} s on l.app_name = s.app_name
left join {{ ref('oui_lookup') }} o on left(replace(l.device_mac, ':', ''), 6) = o.oui
```

**Dữ liệu tham chiếu (Seeds):**

| Seed file | Số bản ghi | Mô tả |
|---|---|---|
| `app_segments.csv` | ~8 | Gán phân khúc cho mỗi `app_name` (VOD, Sport, Kids, …) |
| `oui_lookup.csv` | 39k+ | Tra cứu 3 byte đầu của MAC sang tên hãng sản xuất |

Việc join qua `left join` đảm bảo không mất bản ghi ngay cả khi thiếu mapping (giá trị được gán 'Unknown').

Materialized là **view** vì nó chỉ là bước trung gian và không lưu trữ thêm – các mart sẽ quét qua nó khi cần.

## 5. Tầng Mart — Star Schema

Tầng cuối cùng tạo ra các bảng dimension và fact để tiêu thụ.

### 5.1. Dimension Tables (SCD Type 1, materialized = table)

#### `dim_app`

```sql
select
    {{ dbt_utils.generate_surrogate_key(['app_name']) }} as app_key,
    app_name,
    app_segment
from {{ ref('int_enriched_sessions') }}
group by app_name, app_segment
```

#### `dim_device`

```sql
select
    {{ dbt_utils.generate_surrogate_key(['device_mac']) }} as device_key,
    device_mac,
    device_vendor
from {{ ref('int_enriched_sessions') }}
group by device_mac, device_vendor
```

#### `dim_contract`

```sql
select
    {{ dbt_utils.generate_surrogate_key(['contract_id']) }} as contract_key,
    contract_id
from {{ ref('int_enriched_sessions') }}
group by contract_id
```

#### `dim_date`

```sql
select distinct
    batch_date as date_key,          -- hoặc có thể tạo surrogate
    to_date(batch_date, 'YYYYMMDD') as full_date,
    left(batch_date, 4) as year,
    substring(batch_date, 5, 2) as month,
    right(batch_date, 2) as day
from {{ ref('int_enriched_sessions') }}
```

(Lưu ý: nếu sau này `batch_date` được chuyển sang `DATE`, logic sẽ đơn giản hơn nhiều.)

Các bảng dimension này được materialize thành **table** (full refresh mỗi lần chạy) vì:
- Số lượng dòng nhỏ: `dim_app` (8), `dim_device` (vài trăm), `dim_contract` (vài nghìn), `dim_date` (vài trăm).
- BI tools cần response nhanh khi join fact với dim – table tốt hơn view vì tránh quét lại dữ liệu thô.

### 5.2. Fact Table — `fact_views` (Incremental)

```sql
{{ config(
    materialized='incremental',
    unique_key='event_id',
    sort='batch_date',
    dist='key'
) }}

select
    {{ dbt_utils.generate_surrogate_key(['event_id']) }} as fact_key,
    e.event_id,
    d_app.app_key,
    d_dev.device_key,
    d_con.contract_key,
    d_dat.date_key,
    e.total_duration_seconds,
    e.total_duration_minutes
from {{ ref('int_enriched_sessions') }} e
left join {{ ref('dim_app') }} d_app on e.app_name = d_app.app_name
left join {{ ref('dim_device') }} d_dev on e.device_mac = d_dev.device_mac
left join {{ ref('dim_contract') }} d_con on e.contract_id = d_con.contract_id
left join {{ ref('dim_date') }} d_dat on e.batch_date = d_dat.date_key

{% if is_incremental() %}
where e.batch_date > (select max(batch_date) from {{ this }})
{% endif %}
```

**Thiết kế:**
- **Incremental**: chỉ load dữ liệu mới của ngày mới, dựa trên `batch_date` từ intermediate. Với lượng dữ liệu lớn (45.9M rows/tháng), full rebuild không khả thi.
- **Surrogate key**: `fact_key` giúp BI tools dễ sử dụng (mặc dù không thực sự cần thiết trong incremental).
- **Sort key trên `batch_date`** để tối ưu filter theo ngày.
- Các khóa ngoại (`app_key`, ...) liên kết với các dimension.

**Tổng hợp dữ liệu theo ngày (aggregation) có thể được thực hiện thông qua các model riêng biệt (ví dụ: `rpt_daily_app_usage`) hoặc ngay trong BI layer.**

## 7. Chiến lược kiểm thử (Testing Strategy)

### 7.1. Staging layer

```yaml
models:
  - name: stg_iptv__logs
    columns:
      - name: event_id
        tests: [unique, not_null]
      - name: contract_id
        tests: [not_null]
      - name: device_mac
        tests: [not_null]
      - name: total_duration_seconds
        tests:
          - not_null
          - dbt_utils.accepted_range:
              min_value: 1
              max_value: 86400
      - name: app_name
        tests:
          - not_null
          - accepted_values:
              values: ['CHANNEL','VOD','CHILD','KPLUS','RELAX','SPORT','FIMS']
```

### 7.2. Intermediate layer

- Kiểm tra rằng các join không làm mất dữ liệu (số dòng `int_enriched_sessions` bằng số dòng `stg_iptv__logs`).
- Có thể thêm custom test kiểm tra tỉ lệ mapping NULL của app_segment và device_vendor.

### 7.3. Mart layer

- **Dimension tables:** unique key (`app_key`, `device_key`, ...), not null.
- **Fact table:**
  - `fact_key` unique, not null.
  - Số dòng mỗi lần chạy incremental khớp với intermediate trong khoảng `batch_date` mới.
  - Referential integrity: không có khóa ngoại nào NULL (inner join thực ra đã bảo đảm, nhưng vẫn nên test để chắc chắn).

Tất cả tests được chạy qua task `test_dbt` trong Airflow.

## 9. Cấu hình Redshift (khuyến nghị)

- **`staging.viewing_history`**: `DISTKEY(contract_id)`, `SORTKEY(batch_date)`.
- **`fact_views`**: `DISTKEY(app_key)` hoặc `DISTSTYLE AUTO`, `SORTKEY(batch_date)`.
- Các bảng dimension nhỏ có thể dùng `DISTSTYLE ALL`.

Những cấu hình này có thể được định nghĩa trực tiếp trong model dbt (sử dụng `config`) hoặc trong DDL khi tạo bảng.
